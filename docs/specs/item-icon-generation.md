# Item Icon Generation Spec

## Background

Item details, avatar equipment, region shops and future custom content need stable pixel-art icons. The portrait system already exists separately; this plan only covers non-portrait item assets.

First batch scope:

- Weapons: `static/game_configs/weapon.csv`
- Elixirs: `static/game_configs/elixir.csv`
- Auxiliary equipment: `static/game_configs/auxiliary.csv`
- Techniques: `static/game_configs/technique.csv`
- Goldfingers: `static/game_configs/goldfinger.csv`

Ecology resource scope:

- Materials: `static/game_configs/material.csv`
- Animals: `static/game_configs/animal.csv`
- Plants: `static/game_configs/plant.csv`
- Lodes: `static/game_configs/lode.csv`
- Formation plates / formation props: if they change in the future from pure numeric configuration into carryable items, they should be merged into the item icon system
- Hidden domains / regions / sects are not part of this system; they are map or panel visual assets and should not be mixed with item icons

## Goals

1. Batch-generate reviewable, reproducible pixel-art item icons.
2. Support generating 3x3 or 4x4 contact sheet large images, then splitting them into single images.
3. Use a solid-color background at generation time, and convert to transparent PNG in post-processing.
4. The frontend displays icons via stable keys and supports a fallback image.
5. API keys may only come from environment variables or a gitignored `.env` file, and must never enter git.

## Non-Goals

1. Do not generate portraits for avatars.
2. Do not call the fal, Tabcode or OpenAI image APIs directly from the frontend.
3. Do not ship raw large images, intermediate split images or keys in the release package.

## Tool Structure

The current tool directory is `tools/item_icons/`:

- `config.py`: reads the Tabcode/OpenAI-compatible configuration.
- `client.py`: Tabcode/OpenAI-compatible image calls.
- `utils/fal_client.py`: fal queue image calls, polling and downloading.
- `build_manifest.py`: generates the to-be-generated manifest from the CSVs.
- `prompts.py`: contact sheet prompt construction.
- `postprocess.py`: splitting, green-screen alpha, pixelation.
- `generate_preview_sheet.py`: generates only one 3x3 preview large image and processes the small images, for manual acceptance.

Key conventions:

- Tabcode: `ITEM_ICON_API_KEY`
- fal: `FAL_KEY` or `ITEM_ICON_FAL_KEY`
- The local `.env` must be ignored by `tools/item_icons/.gitignore`.

## Provider Strategy

### Tabcode

Tabcode is an OpenAI Images API compatible interface:

- Base URL: `https://api2.tabcode.cc/openai/draw/v1`
- Endpoint: `/images/generations`
- Model: `gpt-image-2`
- Response: `data[0].b64_json`

### fal

fal uses the queue API:

- Submit: `POST https://queue.fal.run/{model}`
- Auth: `Authorization: Key <FAL_KEY>`
- Default model: `openai/gpt-image-2`
- Input: `prompt`, `image_size`, `quality`, `num_images`, `output_format`
- Output: `images[0].url`

URLs generated by fal must be downloaded locally immediately, because remote media URLs have a retention period.

## Generation Batches

Run one preview before formal batch generation:

```powershell
$env:ITEM_ICON_FAL_KEY="..."
python -m tools.item_icons.generate_preview_sheet
```

After the preview passes, run the batch:

1. `python -m tools.item_icons.build_manifest`
2. Group by category, visual similarity and level of abstraction.
3. Concrete items prefer 4x4; abstract items prefer 3x3.
4. For each batch, save the prompt, provider, model, request_id, remote URL and local output path.
5. After manual spot checks, publish to `web/src/assets/icons/items/`.

## Post-Processing

1. Save the raw large image to `raw/`.
2. Split by fixed rows/columns into `split/`.
3. Convert the `#ff00ff` background to alpha and save to `alpha/`. Post-processing must not key out by exact color only; it must support edge sampling, removal of the background connected region, and cleanup of small noise connected regions.
4. Pixelate uniformly to 128x128 PNG and save to `pixel/`.
5. Pre-publish checks:
   - PNG sizes are uniform.
   - The four corners are transparent.
   - The subject is non-empty.
   - File names align with manifest keys.

## Frontend Integration Design

Suggested additions:

- `web/src/assets/icons/items/*.png`
- `web/src/utils/itemIcons.ts`

Resolution order:

1. Exact match on `item.icon_key`.
2. Infer using `item.icon_category + item.id`.
3. Use a type/category fallback.
4. Use `fallback_unknown`.

Display locations:

- `EntityRow.vue`: a fixed 24-28px icon to the left of the name.
- `EntityDetailCard.vue`: a fixed 48-64px icon in the title area.

The backend DTO can later add optional fields:

- `icon_key`
- `icon_category`

The first version can also infer on the frontend, and have the backend provide them explicitly once the custom content pipeline is stable.

## Scope Assessment

Besides the weapons, elixirs, auxiliary equipment, techniques and goldfingers listed by the user, I recommend including "materials" in the second batch as well. Materials appear in avatar details, drops, gathering, shops and event rewards, and their names are highly recognizable, so the benefit of icons is obvious.

Not recommended for now:

- Avatars: portraits already exist.
- Sects / regions / hidden domains: these belong to the map or organization visual system, not items.
- Emotions, aptitudes, races, Dao lineages: better suited to tags or small symbols, not suited to being mixed into the same generation batch as item icons.
